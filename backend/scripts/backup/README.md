# Слепки базы: как это работает и что делать, когда всё упало

PostgreSQL хранит аккаунты, коллекции, отзывы, переписку и ссылки на медиа.
Обработанные изображения хранятся отдельно, в production — в S3. Дамп базы
не содержит бинарные изображения. Резервирование и восстановление бакета
проверяются отдельно.

## Три скрипта

| Скрипт | Что делает |
|---|---|
| `db-backup.cjs` | дамп → (шифрование) → (выгрузка в S3) → ротация |
| `db-verify.cjs` | разворачивает дамп во временную базу и сверяет счётчики строк |
| `db-restore.cjs` | восстановление; без `--yes` только показывает план |

Все три по умолчанию работают через docker-контейнер `postgres`.
Переопределяется переменными: `PG_CONTAINER`, `PG_USER`, `PG_DB`, `BACKUP_DIR`.
Если `PG_USER` и `PG_DB` заданы явно, `backend/.env` не читается. Иначе имя
пользователя и базы берутся из `DATABASE_URL` этого файла. Пустой `PG_CONTAINER`
означает локальные утилиты PostgreSQL, которым при необходимости нужны
`PGHOST`, `PGPORT` и обычные настройки аутентификации PostgreSQL.

`pg_dump` запускается **внутри контейнера** — так версия клиента всегда совпадает
с версией сервера. Дамп с хоста ломается, как только сервер новее клиента.

## Ежедневная эксплуатация

```bash
cd /srv/favorite/deploy
# снять слепок, используя приватную конфигурацию deploy
bash backup.sh

# подготовить настройки для проверки и ручного восстановления
source ./common.sh
export PG_CONTAINER=favorite-postgres PG_USER="$POSTGRES_USER" PG_DB="$POSTGRES_DB"
# проверить восстановление хотя бы раз в месяц
node ../backend/scripts/backup/db-verify.cjs
```

Формат дампа — `-Fc` (custom): сжат и позволяет восстанавливать выборочно,
отдельными таблицами. Готовые файлы появляются после успешного завершения
`pg_dump`, имеют уникальные имена и права `0600`. Прерванный дамп не публикуется
как готовая копия.

Проверка использует новую базу со случайным именем `favourite_verify_*` и
удаляет только её. Расхождение счётчиков завершает проверку с ошибкой. Если
после создания дампа рабочие данные менялись, это само по себе не доказывает
повреждение архива. Сравнивать нужно с соответствующим состоянием данных.

## Расписание

Cron на сервере, каждый час:

```cron
0 * * * * /bin/bash /srv/favorite/deploy/backup.sh >> /var/log/favorite-backup.log 2>&1
```

Ротация по умолчанию: все дампы за последние 24 часа, затем по одному свежему
на день (7), на неделю (4) и на месяц (3). Меняется через `KEEP_HOURLY`,
`KEEP_DAILY`, `KEEP_WEEKLY`, `KEEP_MONTHLY`.

## Копия вне сервера — обязательна

Бэкап на том же диске не спасает ни от смерти диска, ни от удаления VPS.

```bash
export S3_URI="s3://favorite-backups/db"
export GPG_RECIPIENT="you@example.com"   # в дампе email'ы, хеши паролей, переписка
export HEALTHCHECK_URL="https://hc-ping.com/<uuid>"
```

- `S3_URI` — выгрузка через `aws s3 cp`. Ключ доступа выдать **только на запись**:
  взломанный сервер не должен уметь стирать архив.
- `S3_ENDPOINT_URL` — endpoint S3-совместимого провайдера, например `https://s3.twcstorage.ru`. Нужны AWS CLI и отдельные `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION=ru-1`. Ключи `MEDIA_S3_*` не используются скриптом бэкапа.
- `GPG_RECIPIENT` — дамп шифруется, локальная незашифрованная копия удаляется.
  Приватный ключ хранить НЕ на этом сервере, иначе шифрование бессмысленно.
- `HEALTHCHECK_URL` — dead-man switch: cron падает молча, а сервис напишет вам,
  если очередного пинга не было.

## Когда всё упало

```bash
# Команды из backend/, после настройки PG_* и BACKUP_DIR
# 1. посмотреть план, ничего не меняя
node scripts/backup/db-restore.cjs backups/favorites-2026-07-28T1112Z.dump

# 2. безопасный путь: развернуть рядом и проверить глазами
node scripts/backup/db-restore.cjs backups/favorites-....dump --into favorites_new --yes
#    затем поменять базу в DATABASE_URL на favorites_new и перезапустить backend

# 3. поверх рабочей базы (перед этим скрипт сам снимет страховочный дамп)
node scripts/backup/db-restore.cjs backups/favorites-....dump --into favorites --yes
#    после восстановления перезапустить backend: соединения в пуле смотрят на прежние объекты
```

Новая цель должна отсутствовать. Если база с таким именем уже существует,
скрипт отказывает и не удаляет её. Выберите другое имя.

Восстановление выполняется одной транзакцией с остановкой при первой ошибке.
При восстановлении поверх рабочей базы ошибка не оставляет частично изменённую
схему. До этой операции сохраняется отдельный страховочный дамп. Ошибка его
создания отменяет восстановление. Перед восстановлением рабочей базы вручную
остановите записи приложения и проверьте выбранные файл и цель.

Зашифрованный дамп сначала расшифровать: `gpg --decrypt file.dump.gpg > file.dump`.

## Деплой и миграции — важное для этого проекта

Применять сохранённую историю через `yarn prisma migrate deploy`.
Не использовать `migrate resolve --applied` для обхода ошибки неприменённого
SQL. Чистый стенд проверяется сценарием `bash deploy/verify-local.sh` из корня
репозитория.

Порядок на сервере:

1. `node scripts/backup/db-backup.cjs` — слепок ДО миграции;
2. `yarn prisma migrate deploy`.
3. проверить, что приложение поднялось;
4. только потом переключать трафик.

Если `migrate deploy` спотыкается, сохранить вывод ошибки и выяснить состояние
миграции. Восстановление из дампа — отдельное ручное решение после проверки
на новой базе и оценки совместимости схемы с приложением.

Дамп включает таблицу `_prisma_migrations`, поэтому восстановленная база помнит,
какие миграции применены, и Prisma не пытается накатить их заново.

Локальные регрессионные проверки без PostgreSQL и приватных настроек:

```bash
node --test backend/scripts/backup/backup.spec.cjs
```

Полный Docker smoke дополнительно проверяет backup → verify → restore,
сохранение роли и версии сессии, историю миграций, отказ для занятой базы и
откат при SQL-ошибке. Успех этапа — `FAVOURITE_BACKUP_RESTORE_OK`, всего сценария —
`FAVOURITE_DOCKER_CHECK_OK`. Это не подтверждает доступность внешнего S3,
шифрование или восстановление production.

**Демо-данные не должны попасть в прод.** `scripts/seed-demo-movies.cjs` помечает
тайтлы `[demo]` в описании и умеет `--remove`.

## Чего не делать

- Держать бэкапы только на сервере с базой.
- Не проверять восстановление (`db-verify.cjs` существует ровно для этого).
- Класть креды S3 и приватный gpg-ключ в репозиторий.
- Считать реплику бэкапом: реплика повторит и `DROP TABLE`, и порчу данных.
