# Изображения: устройство, URL и хранилище

Реализация 4 октября 2026 года. Общий `ImagePicker` используется при создании фильма/сериала, замене постера, настройке собственного профиля и редактировании фото актёра. Дизайн основной оболочки сохранён.

## Как работает

Файл отправляется бинарным multipart в API, обрабатывается в worker и сохраняется как две WebP-версии. Форма получает URL и `assetId`. При сохранении родительской записи передаётся идентификатор. Blob нужен только для временного предпросмотра, base64 в базе нет. Сервер не скачивает внешние URL.

URL-режим применяется при выходе из поля, кнопкой «Показать» или Enter. Поэтому нажатие сохранения не игнорирует только что введённую ссылку. Ссылка должна быть HTTP(S), без встроенных логина и пароля. Для production использовать HTTPS. Нерабочая внешняя ссылка показывает fallback. Ошибка замены файла сохраняет предыдущую картинку, поздний ответ старой загрузки не заменяет новый выбор.

Фотографии публичные. Загруженные оригиналы не сохраняются. Метаданные удаляются, маленькие изображения не растягиваются. Отмена новой загрузки не удаляет уже используемую фотографию.

## Контракт API

- `GET /uploads/image-policy`: публичные размеры и ограничения по назначению.
- `POST /uploads/images`: Bearer JWT, multipart с одним `file` и одним `purpose`. Назначение: `MOVIE_POSTER`, `USER_AVATAR`, `ACTOR_PHOTO`. Успех 201: `id`, `url`, `thumbnailUrl`, `mimeType`, `byteSize`, `width`, `height`.
- `DELETE /uploads/images/:id`: только собственное непривязанное медиа, успех 204. Привязанный файл возвращает 409.
- `POST /movies`, `PATCH /movies/:id`: `posterAssetId` для файла либо `imageUrl` для внешней ссылки. При очистке постера поля передаются как `null`.
- `PATCH /users/:id`: `avatarAssetId` либо `avatarUrl`. Фото и имя сохраняются одной операцией. Обычный пользователь меняет только свой профиль.
- `PATCH /actors/:id`: `imageAssetId` либо `imageUrl`, автор или ADMIN.
- `GET /media/images/:id/full.webp`, `thumbnail.webp`: локальная разработка. Production раздаёт картинки из S3.

Нельзя отправить непустые `assetId` и URL одновременно. Собственные media URL также превращаются в управляемую связь, поэтому очистка не оставляет ссылку на уже удалённую временную загрузку. Связь с родительской записью и освобождение предыдущего файла выполняются в одной Prisma-транзакции.

## Разработка

```bash
cd backend
yarn install --frozen-lockfile
yarn prisma generate
yarn prisma migrate deploy
yarn start:dev
```

В другом терминале:

```bash
cd frontend
yarn install --frozen-lockfile
yarn dev
```

Для локальной разработки без S3 используются `MEDIA_STORAGE=local`, каталог `.media` и адрес `http://localhost:3005/media`. `MEDIA_LOCAL_DIR` и `MEDIA_PUBLIC_BASE_URL` можно задать отдельно. При изменении PORT нужно также изменить публичный адрес media и адрес API фронтенда.

Миграция `20261004140000_shared_image_media` добавляет таблицу, enum и необязательные связи. `yarn prisma migrate deploy` применяет отсутствующие миграции. Не применять `db push`, `migrate reset` или ручное удаление данных к базе с пользовательскими данными.

Не запускать `nest build` в тот же `dist`, пока пользовательский watch его изменяет. Для отдельной проверки можно использовать `tsc -p tsconfig.build.json --outDir /tmp/favourite-check-dist --incremental false`. На сервере образ собирается изолированно, такого конфликта нет.

## Production

Настройка S3, Docker, HTTPS и резервных копий находится в [deploy/README.md](../deploy/README.md). В production локальный диск для изображений намеренно не выбирается. Публичный базовый адрес не должен содержать credentials, query или fragment. Готовые файлы имеют уникальные ключи и immutable cache, при замене URL меняется.

API не содержит интерфейса загрузки видео. Этапы видеоссылок и видеофайлов после production-запуска сохранены в [спецификации](media-spec.md).
