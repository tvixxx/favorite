# Обновление и возврат FavouriteApp

Команды выполнять из `/srv/favorite/deploy` на настроенном сервере.
Первый запуск выполняется через `bootstrap.sh`, обновления — через `deploy.sh`.
Не запускать одновременно обновление и откат.

## Что сохраняется автоматически

Перед обновлением `deploy.sh` сохраняет прежние образы backend/web в `images.tar`,
Compose, nginx и копию инструмента восстановления. После сборки новой версии,
но **до миграций**, создаётся полный дамп PostgreSQL и фиксируется её история
миграций. Ошибка любого из этих шагов запрещает запуск миграций и новой версии.

Точки находятся в `$BACKUP_DIR/releases/ID`. Каталог точки закрыт правами `0700`,
дамп — `0600`. Метаданные `point.json` содержат время, идентификаторы образов и
Git HEAD до/после получения кода. Git HEAD — справочная отметка. Для отката
используются сохранённые образы реально существовавших контейнеров.

`READY` означает, что архив образов и дамп подготовлены. `INCOMPLETE` нельзя
использовать для отката. Это не доказательство проверки всех функций приложения.

## Обычное обновление

```bash
bash deploy.sh
# Для уже выбранного кода, без git pull
bash deploy.sh --no-pull
```

В выводе будет `RESTORE_POINT_READY ID`. Сохраните ID вместе с логом обновления.
При ошибке не запускайте деплой многократно подряд, сначала сохраните вывод.

## Вернуть приложение, сохранив новые данные пользователей

```bash
bash rollback.sh list
bash rollback.sh app ID --yes
```

Команда загружает прежние образы из архива, пересоздаёт только backend/web,
проверяет nginx, API и веб. БД, её миграции и изображения не откатываются.
Успех — `FAVOURITE_ROLLBACK_OK ID`.

Если история миграций отличается, команда остановится **до переключения**.
Пришлите ID, ошибку и список новых миграций. После анализа обратной совместимости
можно выполнить `bash rollback.sh app ID --schema-compatible --yes`.
Незавершённую миграцию этим флагом обойти нельзя.

Без `--yes` оба режима отката только показывают план.

## Вернуть БД и приложение к точке

Этот вариант удаляет все изменения БД после создания дампа, включая новые
регистрации, отзывы и сообщения. Применять только после явного решения о такой
потере данных.

```bash
bash rollback.sh list
bash rollback.sh database ID --yes
```

Команда проверяет архив образов, останавливает backend/web, сохраняет
страховочный дамп текущей БД в `$BACKUP_DIR/releases/safety`, затем восстанавливает
БД одной транзакцией и запускает сохранённые образы. При ошибке восстановления
транзакция откатывается и запускаются те же контейнеры, которые были остановлены.
Если после успешного restore не поднялось приложение, БД уже восстановлена.
Сохраните лог, не повторяйте восстановление автоматически.

Если дамп зашифрован, приватный ключ остаётся на доверенном компьютере.
Сначала расшифруйте выбранный дамп там, затем безопасно перенесите результат
на сервер с правами `0600` и выполните:

```bash
bash rollback.sh database ID --dump /защищённый/путь/копия.dump --yes
```

Восстановление не переключает Git checkout. Следующий `deploy.sh` соберёт код
текущей ветки. Сначала исправьте дефект или вручную выберите нужную версию кода.

## Какие логи передать для диагностики

```bash
bash rollback.sh list
docker compose ps
docker compose logs --tail=100 backend web
```

Также нужен полный вывод неудачной команды, ID точки и время ошибки.
Перед передачей удалите из логов токены и другие секреты. `.env`, ключи и дампы
в чат не отправлять.

## Границы восстановления

Это возврат приложения и PostgreSQL на том же сервере. `.env`, TLS-ключи,
настройки ОС и бинарные изображения S3 не включаются в точку и не заменяются.
Деплой не меняет приватный env. Его резервную копию и ключи хранить отдельно.
Для возврата удалённых изображений потребуется защита/версионирование S3,
это проверяется при подключении настоящего хранилища.

Архив Docker позволяет вернуть образы после их удаления из локального Docker.
Потерю всего VPS локальные файлы не переживут. Копирование точек вне сервера
нужно настроить отдельно вместе с приватным хранилищем бэкапов.

Точки не удаляются автоматически. Перед обновлениями проверяйте `df -h` и
`du -sh "$BACKUP_DIR"/releases/*`. Архивы образов занимают место. Старые точки
удалять адресно только после решения, какие версии больше не нужны.

## Проверка до production

```bash
node --test deploy/release.spec.cjs backend/scripts/backup/backup.spec.cjs
# Отдельный одноразовый Docker-проект, без рабочей БД и приватного env
node deploy/verify-rollback.cjs
```

Docker-проверка создаёт небольшие версии `old/new`, проверяет возврат образов с
сохранением новых данных, запрет отката при новых миграциях, восстановление БД
и возврат текущих контейнеров после ошибки restore. Удаляет только свой
QA-проект и его файлы. Итог — `FAVOURITE_ROLLBACK_CHECK_OK`.
