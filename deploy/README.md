# Развёртывание FavouriteApp на VPS

Обновлено 8 октября 2026 года. Сохранена исходная схема одного домена: nginx раздаёт Vue, `/api/` проксирует в NestJS, `/socket.io/` обслуживает чат. PostgreSQL доступен только внутри Docker-сети. Обработанные изображения раздаются S3 напрямую.

Код, миграция и локальные сценарии проверяются в этой задаче. Проверки реального S3, Docker-образов, nginx, сертификатов и чистой серверной базы требуют отдельного стенда. Не считать этот документ свидетельством уже выполненного production deploy.

## Конфигурация и расходы

Для старта с друзьями: Ubuntu 24.04, **2 vCPU, 4 ГБ RAM, 50 ГБ NVMe**. Это умеренный ориентир с запасом относительно 2 ГБ, а не гарантия количества пользователей или срока работы. На VPS находятся frontend, backend, Socket.IO и PostgreSQL. Сборки образов выполняются последовательно, поскольку сборка потребляет больше памяти, чем раздача готового фронтенда.

Следить за памятью, задержками API, очередью обработки картинок, свободным диском и расходами S3. Увеличивать CPU/RAM по замерам, а не покупать 8 ГБ заранее. Диск занят базой, Docker-образами и локальными резервными копиями. Изображения не увеличивают основной диск VPS.

- [Облачные серверы Timeweb Cloud](https://timeweb.cloud/services/cloud-servers).
- [S3 и тарифы](https://timeweb.cloud/services/s3-storage).
- [Изменение конфигурации сервера](https://timeweb.cloud/docs/cloud-servers/manage-servers/server-configuration).

VPS и S3 подключаются и оплачиваются отдельно в одном аккаунте Timeweb Cloud. Для изображений подходит стандартный класс хранения. Начать можно с 10 ГБ и увеличить объём по заполнению. Проверить исходящий трафик и автоапгрейд в панели до заказа. Бэкапы базы размещаются в **отдельном приватном бакете**, фотографии пользователей и постеры — в публичном бакете только для готовых изображений.

CPU и RAM можно изменить, но уменьшить основной диск существующего сервера нельзя. Для диска меньшего размера потребуется новый VPS и перенос данных. Поэтому сначала выбрать умеренный диск и вынести медиа в S3. Смена конфигурации требует перезагрузки по инструкции провайдера.

Vercel подходит для собранного Vue. Текущий постоянный NestJS-процесс с Socket.IO и обработчиком изображений практичнее оставить на VPS. Отдельный frontend потребует согласования origin, адресов API/сокета и cookies. Для первого запуска один домен проще.

## Настройки сервера

Создать `deploy/.env` вручную, установить права `chmod 600 deploy/.env`. Файл не хранить в Git, не отправлять в чат и не включать в Docker-образы. Имена переменных ниже — контракт текущего кода, старый `.env.example` может не содержать новые поля.

Обязательны:

- `DOMAIN`, `LETSENCRYPT_EMAIL`, `POSTGRES_USER`, `POSTGRES_DB`, `POSTGRES_PASSWORD`, `JWT_SECRET`.
- `POSTGRES_USER` и `POSTGRES_DB`: буквы, цифры и `_`. Для пароля использовать `openssl rand -hex 32`, результат вписать как значение. Base64-пароль с `/` или `+` нельзя вставлять в PostgreSQL URI без кодирования.
- `JWT_SECRET`: случайное значение, например результат `openssl rand -hex 48`.
- `MEDIA_PUBLIC_BASE_URL`: `https://s3.twcstorage.ru/ИМЯ_БАКЕТА` либо собственный HTTPS-домен изображений. Без `/images` на конце и без query-параметров.
- `MEDIA_S3_ENDPOINT=https://s3.twcstorage.ru`, `MEDIA_S3_REGION=ru-1`, `MEDIA_S3_BUCKET`, `MEDIA_S3_PATH_STYLE=true`, `MEDIA_S3_ACCESS_KEY`, `MEDIA_S3_SECRET_KEY`.

Endpoint, имя бакета и ключи сверять с панелью провайдера. [Официальный пример Timeweb](https://github.com/timeweb-cloud/s3-examples) подтверждает endpoint и регион. [Публичные URL и доступ к бакетам](https://timeweb.cloud/docs/s3-storage/manage-storage/manage-buckets).

Необязательны `DATA_DIR`, `BACKUP_DIR`, `JWT_ACCESS_TOKEN_TTL`, `JWT_REFRESH_TOKEN_TTL`, `COOKIE_DOMAIN`. Compose подставляет значения по умолчанию, пустой `COOKIE_DOMAIN` означает host-only cookie. Производство использует `MEDIA_STORAGE=s3` и `PORT=3005`, эти значения задаёт Compose.

S3-ключ backend должен иметь права записи и удаления только в бакете изображений. В публичный бакет не класть исходные файлы, дампы, ключи и пользовательские документы. CORS бакета для текущей загрузки не нужен: браузер отправляет файл API, API пишет в S3, браузер читает готовое изображение.

## Первый запуск

На чистом сервере установить Git, клонировать свой репозиторий в `/srv/favorite`. В панели открыть HTTP/HTTPS и свой SSH-порт, настроить DNS. До включения UFW проверить, что правило SSH соответствует фактическому порту. Скрипт добавляет профиль OpenSSH, который предполагает стандартный порт.

Из `/srv/favorite/deploy`:

```bash
# Создать и заполнить .env самостоятельно, затем ограничить доступ
chmod 600 .env
bash bootstrap.sh
bash bootstrap.sh certs
bash bootstrap.sh cron
```

Bootstrap устанавливает Docker, Node 22 и служебные пакеты, создаёт каталоги, собирает образы, ждёт PostgreSQL, запускает миграции отдельным контейнером и только потом новую версию backend. HTTP нужен для ACME и проверки `/api/health`. **Авторизация требует HTTPS**, поскольку refresh cookie имеет Secure.

Сертификат генерирует игнорируемый `.state/nginx-ssl.conf`. Скрипты выбирают его через `NGINX_CONFIG`, не редактируя отслеживаемый Compose. Ручной `docker compose` после включения HTTPS запускать с `NGINX_CONFIG` на этот файл, иначе по умолчанию будет HTTP-конфиг. Старое монтирование `app-ssl.generated.conf` из предыдущей инструкции переносится в `.state` вручную при обновлении старого сервера.

PostgreSQL остаётся версии 18, как в исходном deploy. Не менять major и не очищать каталог данных при обновлении. Чистую базу необходимо проверить полным применением истории миграций. Исторические сведения о расхождении локальной схемы и миграций не заменяют эту проверку для текущей версии.

## Обновление

```bash
cd /srv/favorite/deploy
bash deploy.sh
# Для заранее выбранного пользователем commit без git pull
bash deploy.sh --no-pull
```

Порядок: архив прежних образов и конфигурации → получение кода → сборка → проверка PostgreSQL → отдельный полный дамп БД и завершение точки возврата → `prisma migrate deploy` в одноразовом контейнере → готовность backend → пересоздание nginx → проверка API и веба. Ошибка любого шага завершает скрипт. Ответ 500, HTML вместо JSON и отсутствие готовности базы не считаются успехом. Точки хранятся в `$BACKUP_DIR/releases/ID`, успешная подготовка отмечается `RESTORE_POINT_READY ID`.

Старое приложение продолжает работать во время сборки и миграции. Поэтому миграции обновлений должны оставаться совместимыми со старой версией до переключения кода. Удаления и переименования колонок требуют отдельного rollout. Готовые команды возврата образов и отдельного восстановления БД описаны в [RECOVERY.md](RECOVERY.md). Без `--yes` они показывают план. Автоматического разрушительного отката БД нет.

Prisma CLI 7.10.0 запускается через `yarn prisma migrate deploy` в одноразовом сервисе `migrate`, собранном из build-стадии backend. Постоянный runtime API содержит только production-зависимости и скомпилированный клиент. CLI/Studio не публикуются наружу. Не запускать `npx prisma` внутри runtime-контейнера: это может скачать другую версию CLI.

Dockerfile использует `yarn install --frozen-lockfile --production=true` и дополнительно исключает CLI, `@prisma/dev` и `@prisma/config` из runtime. Это сохраняет границу между API и инструментами миграций. Аудит всех зависимостей и аудит `--groups dependencies` проверяются отдельно. Нулевой production-аудит не означает отсутствие замечаний в инструментах сборки и тестов.

Основной менеджер — **Yarn Classic 1.22.22**, источники версий — `backend/yarn.lock` и `frontend/yarn.lock`. Локально и в Docker используется `yarn install --frozen-lockfile`. Проектные `.npmrc` и `.yarnrc` задают `https://registry.npmjs.org/`, адрес Nexus удалён из lock-файла. Глобальные настройки других проектов не меняются. Перед сборкой вне корпоративной сети убедиться, что переменные окружения не переопределяют registry.

## Локальная проверка контейнеров

Из корня репозитория, при запущенном Docker Desktop:

```bash
bash deploy/verify-local.sh
```

Скрипт собирает Linux amd64 образы, проверяет PNG/HEIC в worker, применяет миграции на отдельной пустой PostgreSQL 18, проверяет backup → verify → restore, API, раздачу SPA и конфигурации nginx HTTP/HTTPS. Восстановление сверяет данные пользователя и историю миграций, проверяет отказ для занятой базы и откат при SQL-ошибке. Использует одноразовые тестовые настройки, отдельную Docker-сеть и не публикует порты хоста. Удаляет только созданные им QA-контейнеры, образы и временные файлы. Этап бэкапа завершается `FAVOURITE_BACKUP_RESTORE_OK`, весь сценарий — `FAVOURITE_DOCKER_CHECK_OK`. Это не проверка реального S3, DNS или Let's Encrypt.

Миграция `20261008000000_one_review_per_user_movie` не удаляет старые отзывы. Если есть несколько отзывов одного пользователя на фильм, она останавливается. Сначала явно выбрать сохраняемый отзыв и удалить лишние через интерфейс, затем применять миграцию. Не отмечать неприменённый SQL как `--applied`.

`GET /api/health` проверяет соединение с PostgreSQL. Это readiness, а не полная проверка S3 и всех функций. После обновления проверить вход и refresh после перезагрузки страницы, коллекцию, чат в двух браузерах и загрузку PNG/HEIC. У загрузок nginx лимит 11 МиБ с учётом multipart, сервер проверяет 10 МиБ для постера/актёра и 5 МиБ для аватара. Остальной API ограничен 2 МиБ.

## Бэкапы и обслуживание

`backup.sh` читает приватный `.env`, передаёт `PG_USER`, `PG_DB`, `PG_CONTAINER` и запускает существующий Node-скрипт. Cron содержит только пути wrapper-скриптов, не секретные значения.

Для копии вне VPS установить AWS CLI, добавить отдельные `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION=ru-1`, `S3_URI=s3://ПРИВАТНЫЙ_БАКЕТ/db`, `S3_ENDPOINT_URL=https://s3.twcstorage.ru`. Для шифрования настроить `GPG_RECIPIENT` и импортировать публичный ключ. Приватный ключ восстановления хранить отдельно от VPS. Ключ бэкапа выдать на запись, без удаления старых объектов. Ротация Node-скрипта локальная, для S3 отдельно настроить lifecycle хранилища.

```bash
bash backup.sh
# Смотреть контейнеры и последние логи
docker compose ps
docker compose logs --tail=100 backend web
```

Проверка и восстановление описаны в [инструкции бэкапов](../backend/scripts/backup/README.md). Проверять восстановление на отдельной базе, не ограничиваться наличием файла дампа. Бэкап PostgreSQL не содержит бинарные изображения. Защиту/версионирование бакета и резервное копирование изображений настроить отдельно. Docker-логи ограничены тремя файлами по 10 МБ на контейнер. Старые неиспользуемые образы удалять адресно после проверки новой версии, не выполнять `prune -a` как часть деплоя.
